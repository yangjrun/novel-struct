# 归属评测

版本 0.1 ｜ 对应 `packages/pipeline/src/evaluate-attribution.ts`，命令 `pnpm cli eval <editionId>`

## 1. 目的

结构遍的质量几乎全在说话人归属上。评测回答一个问题：换一个归属器、改一版提示词、换一个模型，在同一批人工标注的对白上准确率是升是降。评测只读数据库，不写任何解析结果，可以随时对任何版本重复运行。

M1 验收标准：LLM 归属器在 50 条金标上准确率不低于 85%。

## 2. 金标格式

JSON Lines，一行一条，空行和 `#` 开头的行忽略。仓库自带 `eval/zhe-you-xi-ye-tai-zhen-shi-le.gold.jsonl`：《这游戏也太真实了》第 1 到 3 章的 50 条。

| 字段 | 必填 | 说明 |
|---|---|---|
| `chapter` | 是 | 章节标题里的编号，`第N章` 的 N。用编号而不是 index，前言、作者的话被识别或漏识别时 index 会漂移，编号不会 |
| `quote` | 是 | 对白内部（不含引号）的一段子串，要在该章的对白里唯一。不要求整句，够唯一即可 |
| `speaker` | 是 | 规范名，也就是实体表里希望出现的 `canonical_name` |
| `aliases` | 否 | 也算正确的其他称呼。群聊里的网名、代词不能算，因为代词“他”对哪句都可能对 |
| `occurrence` | 否 | 同一子串在该章多条对白里出现时，取第几条，从 1 开始 |
| `note` | 否 | 标注理由，给下一个标注者看 |

选条时刻意混合了三类：有紧邻说话标签的（`楚光继续问道。` / `“……”楚光笑了笑说`）、标签隔了一段的、完全无标签靠上下文的一问一答。第一类是启发式的舒适区，后两类是 LLM 该拉开差距的地方。

## 3. 计分

对每条金标：

1. 找到 `chapter` 对应的章，用指定归属器跑一遍结构遍，不提交。已知实体取数据库当前状态，和真实解析看到的一样。
2. 在该章的对白分段里找包含 `quote` 的那条。找不到、或不唯一且没给 `occurrence`，整个评测报错，因为这说明金标写错了，不是模型错了。
3. 分段的说话人已消解到实体则取实体规范名，否则取 surface。等于 `speaker` 或任一 `aliases` 记 `correct`；是 `[unknown]` 或没有 surface 记 `unattributed`；其他记 `wrong`。

`accuracy = correct / total`。未归属单独计数，因为“不知道”比“说错人”对 TTS 的伤害小，改进方向也不同。

## 4. 用法

```bash
# 先导入并确认版本 ID
pnpm cli import "novels/这游戏也太真实了(晨星LL).txt" --title "这游戏也太真实了" --author "晨星LL"

# 启发式基线
pnpm cli eval <editionId>

# LLM，需要 .env 里的 LLM_API_KEY、LLM_MODEL
pnpm cli eval <editionId> --attributor llm --verbose

# 完整 JSON，便于比较两次运行
pnpm cli eval <editionId> --json > eval/out/heuristic.json
```

`--verbose` 逐条列出错误与未归属的对白，是改启发式规则时最直接的反馈。评测过程中每章开始与结束各输出一行到 stderr，模型慢的时候能看出它在动；`--json` 的 stdout 不受影响。

### LLM 请求的超时与重试

一章的段落、对白和已知实体一次性交给模型，输出是几十条归属加实体加场景的 JSON，慢模型要跑一两分钟。为了区分"模型还在想"和"连接死了"，客户端默认用流式（SSE）接收：

| 变量 | 默认 | 含义 |
|---|---|---|
| `LLM_IDLE_TIMEOUT_MS` | 120000 | 首字节之前、或两个数据块之间允许的最长静默。超过判定为卡死，重试该次请求（最多 2 次重试） |
| `LLM_TIMEOUT_MS` | 900000 | 单次请求总时长上限。超过直接失败不重试，因为再慢的模型也不会因为重来而变快 |
| `LLM_STREAM` | true | 服务端不支持 `stream: true` 时设为 `false`，此时只有总时长上限起作用 |
| `LLM_MAX_TOKENS` | 服务端默认 | 限制输出 token 数 |

看到 `LLM request stalled: no data for 120000 ms`，先确认 `LLM_BASE_URL` 从本机可达（`curl -m 10 <base>/models`）；能通再考虑加大 `LLM_IDLE_TIMEOUT_MS`。看到 `exceeded ... ms` 则是模型太慢或输出太长，换更快的模型或设 `LLM_MAX_TOKENS`。

## 5. 基线记录

| 日期 | 归属器 | 版本 | 正确 | 错误 | 未归属 | 准确率 |
|---|---|---|---|---|---|---|
| 2026-09-20 | heuristic | heuristic/0.2 | 21 | 0 | 29 | 42.0% |
| 2026-09-21 | llm | structure-pass/0.1，mimo-v2.5-pro | 50 | 0 | 0 | 100.0% |

启发式的特点是宁可不答也不答错：50 条里 0 条错误，29 条未归属全部是无标签的一问一答（“你能别冷不丁地开口吗？”“好的主人。”）和标签隔了一段的情况。这正是留给 LLM 归属器的空间；第 1 到 3 章的对话几乎都在楚光与小柒、群聊网友之间，有上下文就能判断。

LLM 一次跑通即全对，M1 的 85% 验收线达成。代价是时间和 token：三章分别用时 168 s、170 s、107 s，输入 14896 token，输出 24194 token。输出远大于输入是因为模型把实体描述和场景概括写得很长，后续可用 `LLM_MAX_TOKENS` 或收紧提示词。两章的场景划分没有首尾相接，回退成单场景（`scene proposals do not tile the chapter`）；这不影响归属，但说明场景切分的提示词还要调。金标只覆盖前三章，说话人也只有五六个，100% 不代表全书水平，M2 扩到 20 章后再看。

## 6. 已知限制

- 引号抽取不区分对白和强调：`确实有“五个”` 里的 `“五个”` 也成了对白候选，启发式还会把前面的 `盲盒开出来` 误读成 `盲盒` 在说话。金标里没有这类引号，所以不影响准确率数字，但会污染实体表。M4 之前先靠 LLM 归属器的 `speaker: null` 处理，之后考虑在抽取阶段按长度与标点过滤。
- `note` 类章节目前也会被 `parse` 解析，留言里的引号同样会产生说话人。见路线图未决问题。
