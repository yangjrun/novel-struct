# 归属评测

版本 0.1 ｜ 对应 `packages/pipeline/src/evaluate-attribution.ts`，命令 `pnpm cli eval <editionId>`

## 1. 目的

结构遍的质量几乎全在说话人归属上。评测回答一个问题：换一个归属器、改一版提示词、换一个模型，在同一批人工标注的对白上准确率是升是降。评测只读数据库，不写任何解析结果，可以随时对任何版本重复运行。

M1 验收标准：LLM 归属器在 50 条金标上准确率不低于 85%。

## 2. 金标格式

JSON Lines，一行一条，空行和 `#` 开头的行忽略。仓库自带 `eval/zhe-you-xi-ye-tai-zhen-shi-le.gold.jsonl`：《这游戏也太真实了》第 1 到 3 章的 50 条。

| 字段 | 必填 | 说明 |
|---|---|---|
| `chapter` | 是 | 章节标题里的编号，`第N章` 的 N。用编号而不是 index，前言、作者的话被识别或漏识别时 index 会漂移，编号不会 |
| `quote` | 是 | 对白内部（不含引号）的一段子串，要在该章的对白里唯一。不要求整句，够唯一即可 |
| `speaker` | 是 | 规范名，也就是实体表里希望出现的 `canonical_name` |
| `aliases` | 否 | 也算正确的其他称呼。群聊里的网名、代词不能算，因为代词“他”对哪句都可能对 |
| `occurrence` | 否 | 同一子串在该章多条对白里出现时，取第几条，从 1 开始 |
| `note` | 否 | 标注理由，给下一个标注者看 |

选条时刻意混合了三类：有紧邻说话标签的（`楚光继续问道。` / `“……”楚光笑了笑说`）、标签隔了一段的、完全无标签靠上下文的一问一答。第一类是启发式的舒适区，后两类是 LLM 该拉开差距的地方。

## 3. 计分

对每条金标：

1. 找到 `chapter` 对应的章，用指定归属器跑一遍结构遍，不提交。已知实体取数据库当前状态，和真实解析看到的一样。
2. 在该章的对白分段里找包含 `quote` 的那条。找不到、或不唯一且没给 `occurrence`，整个评测报错，因为这说明金标写错了，不是模型错了。
3. 分段的说话人已消解到实体则取实体规范名，否则取 surface。等于 `speaker` 或任一 `aliases` 记 `correct`；是 `[unknown]` 或没有 surface 记 `unattributed`；其他记 `wrong`。

`accuracy = correct / total`。未归属单独计数，因为“不知道”比“说错人”对 TTS 的伤害小，改进方向也不同。

## 4. 用法

```bash
# 先导入并确认版本 ID
pnpm cli import "novels/这游戏也太真实了(晨星LL).txt" --title "这游戏也太真实了" --author "晨星LL"

# 启发式基线
pnpm cli eval <editionId>

# LLM，需要 .env 里的 LLM_API_KEY、LLM_MODEL
pnpm cli eval <editionId> --attributor llm --verbose

# 大范围评测：单章被服务端拒绝时继续，按章汇报；可用 --from/--to 仅重跑指定章节编号
pnpm cli eval <editionId> --gold eval/zhe-you-xi-ye-tai-zhen-shi-le.ch4-20.gold.jsonl \
  --attributor llm --continue-on-error

# 完整 JSON，便于比较两次运行
pnpm cli eval <editionId> --json > eval/out/heuristic.json

# 跨第 4 到 20 章抽样待人工标注的对白，跳过现有金标，不覆盖已有文件
pnpm cli eval-sample <editionId> --from 4 --to 20 --per-chapter 5 \
  --gold eval/zhe-you-xi-ye-tai-zhen-shi-le.gold.jsonl \
  --output eval/zhe-you-xi-ye-tai-zhen-shi-le.draft.jsonl
```

`--verbose` 逐条列出错误与未归属的对白，是改启发式规则时最直接的反馈。评测过程中每章开始与结束各输出一行到 stderr，含该章分数与模型上报的 token；`--json` 的 stdout 不受影响。`--continue-on-error` 将服务端拒绝或归属器异常记为**该章未评测**，继续其他章节，最终返回非零退出码；准确率分母只包含已作答的金标条目，`requestedTotal` 和 `failures` 记录覆盖情况。`--from/--to` 使用金标章节编号，可单独续跑失败章；默认仍在第一个模型错误时停止，金标定位错误始终报错而不计作模型拒绝。

`eval-sample` 只用存储的规范化章节与确定性引号抽取器，在指定章节标题编号范围内均匀选取候选；重复运行选中相同对白。它输出 `speaker: null`（待人工核对，不能直接送入 `eval`）、原文偏移和上下文。完整对白在同一章重复时自动写入 1-based `occurrence`；填入规范名及必要别名后，保留 `chapter`、`quote`、`occurrence`、`speaker`、`aliases` 即可作为现有金标导入（`charStart`、`charEnd`、`context` 仅供标注时参考）。命令不会覆盖已有草稿，也不会自动推断或伪造说话人。

已从导入的 EPUB 版本生成 `eval/zhe-you-xi-ye-tai-zhen-shi-le.ch4-20.draft.jsonl`：第 4–20 章共 85 条候选。根据候选原文上下文核对，删除引号标出的术语、匿名发言和不能可靠判断的归属后，得到独立金标 `eval/zhe-you-xi-ye-tai-zhen-shi-le.ch4-20.gold.jsonl`，覆盖 17 章 63 条对白、多个新角色。原前三章金标仍单独保留，方便直接比较历史基线。第 16 章有一条原文引号未闭合，抽取器按段落末尾截取，评测进度会显示警告。

### LLM 请求的超时与重试

一章的段落、对白和已知实体一次性交给模型，输出是几十条归属加实体加场景的 JSON，慢模型要跑一两分钟。为了区分"模型还在想"和"连接死了"，客户端默认用流式（SSE）接收：

| 变量 | 默认 | 含义 |
|---|---|---|
| `LLM_IDLE_TIMEOUT_MS` | 120000 | 首字节之前、或两个数据块之间允许的最长静默。超过判定为卡死，重试该次请求（最多 2 次重试） |
| `LLM_TIMEOUT_MS` | 900000 | 单次请求总时长上限。超过直接失败不重试，因为再慢的模型也不会因为重来而变快 |
| `LLM_STREAM` | true | 服务端不支持 `stream: true` 时设为 `false`，此时只有总时长上限起作用 |
| `LLM_MAX_TOKENS` | 服务端默认 | 限制输出 token 数 |

看到 `LLM request stalled: no data for 120000 ms`，先确认 `LLM_BASE_URL` 从本机可达（`curl -m 10 <base>/models`）；能通再考虑加大 `LLM_IDLE_TIMEOUT_MS`。看到 `exceeded ... ms` 则是模型太慢或输出太长，换更快的模型或设 `LLM_MAX_TOKENS`。

结构遍遇到不合法的 JSON 会重新请求一次，仍失败则显示总字符数和出错位置附近的内容；若响应里有 `finish_reason: length`，表示服务端因输出长度限制截断，可检查 `LLM_MAX_TOKENS` 或服务端默认上限。符合 JSON 语法但未通过结构校验的输出不会自动重试。

启发式的特点是宁可不答也不答错：50 条里 0 条错误，29 条未归属全部是无标签的一问一答（“你能别冷不丁地开口吗？”“好的主人。”）和标签隔了一段的情况。这正是留给 LLM 归属器的空间；第 1 到 3 章的对话几乎都在楚光与小柒、群聊网友之间，有上下文就能判断。

LLM 一次跑通即全对，M1 的 85% 验收线达成。代价是时间和 token：三章分别用时 168 s、170 s、107 s，输入 14896 token，输出 24194 token。输出远大于输入是因为模型把实体描述和场景概括写得很长，后续可用 `LLM_MAX_TOKENS` 或收紧提示词。两章的场景划分没有首尾相接，回退成单场景（`scene proposals do not tile the chapter`）；这不影响归属，但说明场景切分的提示词还要调。金标只覆盖前三章，说话人也只有五六个，100% 不代表全书水平，M2 扩到 20 章后再看。

后续结构遍提示词已更新至 `structure-pass/0.2`：明确首尾和相邻场景段落边界；若模型返回的场景起点有效但 endParagraph 有缺口/重叠，按下一场景起点修复并给警告。此后的引号抽取新增保守的叙述术语过滤，版本键为 `structure-pass/0.3+quotes/0.2` / `heuristic/0.3+quotes/0.2`；**本页真实 LLM 结果是在引号过滤前跑的 0.2 版本**，不能作为新版本复评。上表前三章的历史 LLM 结果仍属 0.1，不能当成新提示词的同批对比。

新金标的初始启发式基线为 26/63。与前三章基线不同，新角色、新场景下还出现 10 次**错误归属**：如把“方长紧跟着插嘴”误读成“狂风刚”在说话，以及把下一场发言归给上一段的角色。`heuristic/0.3` 收紧无依据的“人名”猜测与上一段对白后的说话标签，重新评测为 29 正确、0 错误、34 未归属；原前三章仍为 21/50 且 0 错误。启发式选择不猜测无法由局部说话标签确定的归属。引号过滤后，两组金标再次复评均保持该数值。评测命令：

```bash
pnpm cli eval <editionId> --gold eval/zhe-you-xi-ye-tai-zhen-shi-le.ch4-20.gold.jsonl --attributor heuristic --verbose
```

### 第 4–20 章真实模型调用（structure-pass/0.2）

2026-09-23 使用 `mimo-v2.5-pro` 对新金标按章节运行。第 4–7 章第一次运行后第 8 章收到非 JSON 响应中断；分段续跑时第 10、11、18 章多次返回 `The request was rejected because it was considered high risk`。诊断确认是**模型服务拒绝作答**，不是归属错误。第 6、10、11 章随后单独重试成功；第 18 章再次遭拒，仍无有效评测结果。其他章节的成功结果和覆盖情况如下：

| 章节 | 金标条数 | 作答状态 |
|---|---:|---|
| 4–7 | 12 | 最终均成功；第 4 章模型用“老查理”称呼查理，核对原文后加入金标别名 |
| 8–9 | 6 | 重试成功；第 8 章场景边界触发确定性修复警告 |
| 10–17 | 34 | 第 10、11 章先拒绝后重试成功；第 16 章原文引号未闭合 |
| 18 | 1 | **服务端拒绝，未评测** |
| 19–20 | 10 | 成功 |

共 63 条金标中，**62 条已作答：正确 62、错误 0、未归属 0；另 1 条未作答**。已作答部分准确率为 62/62；覆盖率为 62/63（98.4%），因此这不是完整 20 章全通过的结论。逐章运行有多次重试，这里不汇总为“单次评测”token；失败请求若未返回 usage，也无法据此计算全部成本。新版本的场景切分已观察到至少一次修复，但尚缺对场景质量的人工对照评测。

### 引号过滤后的复评（structure-pass/0.3+quotes/0.2）

2026-09-28 使用 `mimo-v2.5-pro` 对原第 1–3 章金标运行（`--continue-on-error`）：

| 章节 | 金标条数 | 用时 | 结果 |
|---|---:|---:|---|
| 1 | 21 | 218.7 s | **服务端拒绝**：输出约 3600 字符后以 `finish_reason: content_filter` 截断 |
| 2 | 12 | 195.0 s | **服务端拒绝**：`The request was rejected because it was considered high risk` |
| 3 | 17 | 137.8 s | 17 正确、0 错误、0 未归属；输入 5334、输出 8953 token |

已作答 17/50，全部正确。第 1、2 章在 0.1 版本时均成功作答，这次遭拒，说明服务端风控对同一原文并不稳定，与第 4–20 章观察到的"先拒绝、重试成功"一致。因此**新版本在前三章上尚无完整结论**，需择时单独续跑 `--from 1 --to 2`。

此前 `content_filter` 截断会被当成"JSON 不合法"重试两次后报错，掩盖了拒答原因；现在它与 `high risk` 同样归为 `LlmRequestRejectedError`，评测里记作"模型服务拒绝"。

## 6. 已知限制

- 引号抽取已为带叙述语法标记的短术语（例如 `确实有“五个”`、`以“第四天灾”的身份`）保留旁白分段并记录警告；纯长度不足以区分短对白，因此其余有歧义的引号仍作为候选，未来需在更大真实语料上检验误过滤率。
- `note` 和 `front_matter` 现默认跳过解析；显式指定 `--all-kinds` 时，留言里的引号仍可能产生无意义说话人。

## 7. Jev 影子复核试验

设置 `TYPESAFE_API_KEY` 后，结构遍完成并提交时会调用 TypeSafe `/v1/systemone` 的 Jev 模型，对**有引号的候选**判断对白/心声/术语/不确定；候选包括确定性过滤器已跳过的短术语。一致性遍**单独运行**且提交事实后，会判断原文证据是否支持关系、状态、事件或伏笔断言。影子复核结果单独保存并显示在章节页，永远不修改分段、说话人或事实；复核失败不阻止主解析，详情会显示错误。没有引号的对白不在本轮候选范围内。

给已经解析成功的章节补做结构影子复核时，只需以**相同归属器、相同提示词版本与模型**再次发起解析：成功章节不会重写 IR，会从已存分段补做缺失、失败或不同 Jev 模型版本的影子判断。一致性事实的影子复核在运行一致性遍时同步进行，旧的已成功一致性遍不会自动重新生成事实。

Jev 的接口和现有 OpenAI 兼容解析模型不同；可在 `.env` 中设置 `TYPESAFE_MODEL`（默认固定 `jev-1.13.0`）及 `TYPESAFE_BASE_URL`。固定版本有利于重复评测。影子复核按不超过 8 个候选的小批调用，保留短上下文，避免整章干扰判定；如果模型/服务失败，不会把该章错误地记为通过复核。

中文小说评测先从 `eval/jev-shadow.gold.jsonl` 的人工核对样例开始：

```bash
pnpm cli eval-shadow <editionId> --gold eval/jev-shadow.gold.jsonl --json
```

该命令只读数据库的规范化原文、另行抽取候选并调用 Jev，不修改存储的解析和影子记录。报告分别列出引号用途与证据支持的正确数、模型错误、抽取器未找到的金标及未评测覆盖；对已完成结构遍的章节，另报同批引号候选上主解析的正确数及 Jev 检出的错误、误报、漏检。样例只有少量第 4–6 章的引号与事实断言，是接线与冒烟评测集，不能当作整体中文小说准确率。TypeSafe 官方说明 Jev 的主要训练语言为英语，中文性能需要先扩充金标并对照现有解析结果测量误报、漏报，再考虑让判断参与自动决策。
